可以。既然你已经把 Docker 方案清理干净了，我们现在就按 **Open WebUI 官方源码开发方式**来搭。

不过先纠正一个很重要的点：

> **Open WebUI 官方现在的源码开发文档推荐 `Python 3.11/3.12 + Node.js 22.10+`，并不是直接用 `uv sync`。** 官方开发文档目前给的是 `venv/Conda + pip`；而 `uvx` 是官方提供的“直接运行已发布 Open WebUI 包”的方式。([Open WebUI][1])

但是你希望以后修改源码，我仍然建议你使用 **uv 管理 Python 环境**。只是我们要把它用于**源码项目的 Python 虚拟环境/依赖管理**，而不是把 `uvx open-webui@latest` 当成源码开发。

# 一、我们最终要搭成什么样

你现在的环境：

```text
Windows 11
│
├── PowerShell
│
└── WSL2
     │
     └── Ubuntu
          │
          ├── Git
          ├── Python 3.11
          ├── uv
          ├── Node.js 22+
          │
          └── Open WebUI 源码
               │
               ├── 前端 SvelteKit
               │    └── localhost:5173
               │
               └── 后端 FastAPI
                    └── localhost:8080
```

开发时开两个终端：

```text
终端 1                         终端 2
│                              │
├── npm run dev                └── uv / Python
│                                   ↓
└── 前端 :5173                 后端 :8080
```

浏览器：

```text
http://localhost:5173
```

这正是 Open WebUI 官方源码开发方式：前端和后端分别运行。([Open WebUI][1])

# 二、第一步：确认你在哪个环境

因为你是 **Windows 11 + WSL2**，我建议：

> **源码放在 WSL2 的 Ubuntu 文件系统里面，而不是 `/mnt/c/Users/cjh/...`。**

例如：

```text
~/projects/open-webui
```

而不是：

```text
/mnt/c/Users/cjh/Documents/...
```

这样 Node.js / Python / Git / 文件监听通常会舒服很多。

# 六、克隆 Open WebUI

这里有一个非常重要的官方建议。

Open WebUI 官方开发文档现在明确说：

> **开发应该基于 `dev` 分支，不要直接在 `main` 上开发。**

因为：

```text
dev
 ↓
开发中的最新代码
 ↓
测试
 ↓
发布
 ↓
main
```

而 `main` 是最近一次发布时从 `dev` 截取的版本。([Open WebUI][1])

所以：

```bash
mkdir -p ~/projects
cd ~/projects
```

然后：

```bash
git clone https://github.com/open-webui/open-webui.git
```

进入：

```bash
cd open-webui
```

然后：

```bash
git checkout dev
```

检查：

```bash
git branch
```

应该看到：

```text
* dev
  main
```

# 七、为什么我建议你现在就切 `dev`

因为你的目标不是：

> “下载一个 Open WebUI 稳定版源码看看。”

而是：

> **以后要修改 Open WebUI。**

那么你以后很可能会：

```text
Open WebUI 官方更新
        ↓
dev
        ↓
你的修改
        ↓
定期同步官方代码
```

例如以后：

```bash
git fetch origin
git merge origin/dev
```

或者你建立自己的：

```text
feature/xxx
```

分支。

官方也建议从 `dev` 创建自己的功能分支，而不是直接提交到 `dev`。([Open WebUI][1])

# 十、这里我们用 uv，而不是官方的 venv

官方文档目前写的是：

```bash
python3 -m venv venv
```

然后：

```bash
source venv/bin/activate
```

再：

```bash
pip install -r requirements.txt -U
```

([Open WebUI][1])

但你已经决定使用 uv，所以我建议这里改成：

```bash
uv venv --python 3.11
```

这会创建：

```text
backend/
└── .venv/
```

然后：

```bash
source .venv/bin/activate
```

检查：

```bash
python --version
```

应该是：

```text
Python 3.11.x
```

# 十一、然后安装后端依赖

这里我建议**不要自己猜 `pyproject.toml` / `uv sync` 的方式**。

因为 Open WebUI 官方当前开发流程明确维护的是：

```bash
pip install -r requirements.txt -U
```

所以即使我们使用 uv：

> **让 uv 管理 Python 环境，但使用 Open WebUI 官方维护的 requirements 安装依赖。**

执行：

```bash
uv pip install -r requirements.txt
```

这样实际上是：

```text
uv
 │
 ├── 管理 Python 3.11
 │
 └── 管理 .venv
       │
       └── 安装 Open WebUI requirements.txt
```

比直接：

```bash
pip install
```

更符合你想要的 uv 工作流。

# 十六、但是我们现在不要一次执行全部命令

考虑到你刚刚 Docker 已经遇到过 Open WebUI 当前版本的问题，我建议这次**一步一步验证**，不要直接给你一大串命令让你全部执行。

先做第一阶段：

### 现在你在 WSL2 中执行这 5 个命令：

```bash
git --version
python3 --version
node --version
npm --version
uv --version
```

**把输出贴给我。**

我先根据你 WSL2 当前的 **Python / Node / npm / uv** 版本，判断需要不要补环境。

然后我们再进行：

```text
第 1 步  环境检查       ← 现在
   ↓
第 2 步  Clone + dev
   ↓
第 3 步  uv Python 环境
   ↓
第 4 步  后端依赖
   ↓
第 5 步  前端依赖
   ↓
第 6 步  启动后端
   ↓
第 7 步  启动前端
   ↓
第 8 步  浏览器验证
```

这样出了问题我们能准确知道是 **Python、Node、依赖还是 Open WebUI 本身**，不会再像刚才 Docker 那样一上来就遇到一大串初始化错误。
